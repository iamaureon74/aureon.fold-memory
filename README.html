keep one copy.

fold-memory stores the leftover copies of your files only once: the same log line written every minute, a backup of a backup, a spreadsheet emailed five times. it remembers every path each copy came from, and it hands a file back only if every fingerprint still matches.

the idea in one minute

most storage bills are paid for copies. fold-memory cuts every file into bite-sized pieces, names each piece by its sha-256 fingerprint, and keeps each distinct piece once. a second copy of a file costs a few bytes of bookkeeping. an edit near the start of a big file only creates new pieces around the edit.

how storing works

why a crash loses at most a few seconds

bites go into the pack first and are synced to disk, and only then is the index row that points at them committed. that happens every 2 seconds or every 128 mb. if the power goes out in between, the pack has bytes nobody points at yet, and gc takes them back later. what was committed is held.

how getting back works

unfold, restore and the python read() all follow the same rule: check everything, then hand over the exact bytes or refuse. it never hands back a lookalike.

what is on disk

versions

when a file at a path changes and is ingested again, the version it replaced moves to history. history holds only replaced versions, so a folder that never changes costs nothing extra (about 8 kb on a 642-file test store). a store made by 2.0 gets its history back the first time 2.1 opens it, because the location records were always in the packs.

every capability

numbered in the order a file moves through the tool. 2.1 marks what is new in this version.

storing
  1. content-defined cuttingcut points come from the bytes themselves, so an insert only changes nearby bites. text: 512 b – 16 kb bites; other data: 8 – 256 kb. the cutting runs in c via the standard library.
  2. sha-256 fingerprintsevery bite and every whole file is named by its sha-256. change one bit and the name changes.
  3. one copy of each identical biteacross files, folders, nights and machines. a bite seen twice in the same file is stored once too.
  4. squeeze that knows when to stopzlib with a store dictionary by default; --level fast|default|max (max uses xz); --codec zstd on python 3.14+. jpg, png, mp4, mp3, zip, docx and other already-compressed formats are stored as they are, and so is any bite that doesn't shrink.
  5. append-only pack filesbites live in a few big files (256 mb each by default, set with FOLD_MEMORY_PACK_MB), not millions of tiny ones.
  6. every path rememberedthe same file at a second path costs only a location record. ls shows every path.
  7. fast re-runsfiles with the same size and modification time are skipped without reading. --rehash forces a re-read.
  8. stdin ingestingest - --name nightly.sql folds anything piped in, like database dumps.
  9. parallel and concurrent--jobs N squeezes in parallel; several ingests can write to one store at once.
  10. crash safetybytes are synced before the index points at them, with commits every 2 s or 128 mb. kill -9 loses at most the last few seconds.
  11. bounded memoryfiles of any size are streamed. a 768 mb file peaked at 58 mb of ram (author's measurement, kept as a test).
getting back
  1. exact unfold or refusalevery bite and the whole file are checked; a mismatch exits 1 and leaves nothing half-written. output to a file, a folder or stdout.
  2. three ways to name a filea full fingerprint, a prefix of 6 or more characters, or any path it was seen at.
  3. folder restorerestore <prefix> --out dir keeps the relative layout, modification dates and permissions. --dry-run lists first. 2.1 restoring from / keeps full paths and refuses instead of overwriting when two files would collide.
  4. bounded-memory stdout 2.1files over 32 mb are spooled to disk before being written to stdout, still fully checked first.
  5. version history 2.1versions <path> lists every version held at a path, newest first, with dates. unfold <path> --version N brings one back.
recall
  1. cue: search by wordsranked by where a word appears: in the file name (weight 8), in fields such as title or subject (3), in folder names (2), and in the body text (by frequency).
  2. trance: wider recall--trance adds word-beginning matches, ranks partial matches, and boosts adjacent query words found together. it adds no storage.
  3. reads inside filespdf text and info, word / excel / powerpoint, odf, epub, html titles, json, csv headers, email headers and body, jpeg exif (camera, date), png / gif / webp size, mp3 id3, mp4 / mov / heic boxes, wav / flac / ogg tags, fits headers, sqlite table names, zip / tar / tar.gz member names. every reader is size-bounded, so a zip bomb can't blow up memory.
  4. any languagechinese, japanese and korean are split into character pairs; camelCase and digits are split into their parts.
  5. secrets masked in searchaws, google, github, stripe, openai-style and slack keys, jwts, private-key headers and password= / token= / api_key= text are replaced with [masked] before indexing. 2.1 this now covers metadata fields too (email subjects, csv headers, document titles).
  6. secret-shaped files skipped.env, id_rsa, .pem, .key, .p12, .kdbx, cookies, wallet.dat, .netrc, credentials.json and similar are skipped unless you pass --include-secret-names; .ssh, .gnupg and .password-store folders are never walked.
health
  1. verifyreads and checks every bite and names the files it affects; --full also re-checks every whole file. a bite this python can't decode (zstd on an older python) is reported as "not checked", never as damage.
  2. rebuildrecreates the whole index, including version history, from the packs alone. it rolls back if it can't finish.
  3. reindex 2.1re-reads every held file from its own bites and rebuilds its words and preview, so a 2.0 index can be scrubbed without the original files.
  4. honest statsdisk_bytes is everything on disk (packs, index and dictionary), alongside logical bytes, the saving from copies, the saving from squeezing, and old versions held.
space
  1. forgetdrop one path (with its old versions), a whole file by fingerprint, or a file at every path with --everywhere.
  2. prune 2.1prune --keep N [prefix] keeps the newest N versions per path. the current version and anything still current elsewhere always stay. --dry-run shows the effect first.
  3. gcfrees bites nothing points at and repacks mostly-dead packs. it waits for other writers and leaves anything newer than 1 hour alone. --dry-run, --deep and --force are available.
  4. dupes 2.1identical files sitting at several paths right now, ranked by wasted bytes, with every path listed.
  5. sampleestimates savings for a folder in a temporary store that is deleted afterwards.
moving and fitting in
  1. delta sync between machineshave → export --have → import moves only missing bites. every fingerprint is re-checked on arrival. 2.1 the squeeze dictionary travels too, so stores with different dictionaries can trade.
  2. python libraryFoldMemory(store) with ingest_file, ingest_bytes, ingest_stream, ingest_tree, cue, read, unfold, restore, versions, prune, dupes, verify, stats. failures raise Refused.
  3. inside postgres (11+)add-to-postgres.sql adds fold_column / restore_column to fold old column values into one box per unique value, plus get, verify, gc and stats. it refuses secret-shaped columns. a pg_cron example is included.
  4. self-upgrading storesa 1.0 store upgrades the first time 2.x opens it; a 2.0 store gets its history back from its packs when 2.1 opens it. 2.0 can still read stores and exports written by 2.1.
  5. safe walkingpipes, devices and sockets are skipped (never hang); symlink loops are detected with --follow-links; onedrive / icloud placeholders are skipped unless --hydrate-cloud; names that aren't valid utf-8 are kept exactly.
  6. runs anywhere, offlinepython 3.8+, standard library only: windows, mac, linux, raspberry pi, nas, android (termux), ios (a-shell / pythonista), and air-gapped servers. the store goes to --store, else $FOLD_MEMORY_STORE, else beside the script, else your data folder.
  7. selftest25 checks you can run on your own machine, reporting measured numbers, not claims.

honest limits

unique data does not shrink. savings track how many copies you have, not how much data you have. if your bill is unique photos, unique rows or encrypted disks, plan on about 0–10%. run sample before promising anyone a number.
bytes are stored as they are. secret masking protects the search index, not the stored contents. don't point it at password stores.
a smaller cloud number may not follow. postgres keeps a table's file the same size after a delete until vacuum full or a repack runs, and providers bill the disk you rented, not what you use inside it.

2.1 was tested on python 3.8 and 3.13 (43 tests passed and 1 skipped on each; the skipped zstd test needs 3.14). the postgres file is unchanged from 2.0 and was not re-run for 2.1. speed figures elsewhere in the plain-text readme are the author's own measurements.
